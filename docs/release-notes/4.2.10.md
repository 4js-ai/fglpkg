# fglpkg 4.2.10 — notes for people upgrading

The release body on GitHub is generated from the merged pull requests. This file
holds the things that list cannot say: what changes for you, and what did not
land. Paste it above the generated list when tagging.

## Packages are still published public by default

`fglpkg publish` creates a package with `visibility: "public"` unless the
manifest says otherwise, and there is still no way to change a package's
visibility after it exists. The private half of that work is not in this
release. If a package must not be public, say so in its manifest before the
first publish:

```json
{ "visibility": "private" }
```

A bare `fglpkg publish` with no publish target configured no longer defaults to
the public registry: on a terminal it asks, and anywhere else — `--ci`, a
pipeline, a script — it stops and names the registry it would have used
(GIS-600). That guard is in; the visibility management it was paired with
is not.

## A package packed by 4.2.10 installs on fglpkg 4.2.9

`pack` records what a package's artifacts prove about their character encoding
(GIS-285). Those facts ship in a file of their own inside the archive,
`fglpkg-encoding.json`, and not in the shipped `fglpkg.json`, because fglpkg
4.2.9 and earlier refuse a manifest field they do not know — which would have
cost them the merged `FGLLDPATH` root, `docs`, `run`, and the version in
`list`, for every package packed by 4.2.10.

One thing changes for authors: if you **declare** `characterEncoding`,
`lengthSemantics` or `stringResourceEncodings` in your own `fglpkg.json`, that
project needs fglpkg 4.2.10 or later to work on, because a project's own
manifest is always read strictly. People who install your package are not
affected.

## Artifactory: names are stored lowercase, and old folders are readable

A publish to an Artifactory repository now deploys under the package's
canonical slug, and a lookup canonicalizes too, so a package installs however
its name is typed (GIS-610). A folder left by fglpkg ≤ 4.2.9 under a
mixed-case or dotted name — `DateTime/` rather than `datetime/` — cannot be
installed, which was already true. It can be inspected: `fglpkg search` lists
it, and `fglpkg info DateTime`, spelled exactly as the folder is, describes it
and says that install cannot reach it. Re-publish with 4.2.10, or rename the
folder in Artifactory.

## Known issue: an Artifactory package's Genero range is not enforced on install

A package held in an Artifactory repository installs whatever Genero version it
declares it needs. `fglpkg search` reads that declaration from the version's
sidecar and grades it — `>=7.0.0 ✗` on a Genero 6 machine — and `install` then
installs it anyway, so the two commands can disagree about the same package.

This is not new in 4.2.10 and is not fixed here: the same input behaves the same
way on 4.2.9. What is new is that `search` now shows the declared range for an
Artifactory row (GIS-609), which is what makes the disagreement visible. A
package served by Genero Intelligence is unaffected — its range travels with the
version list, and `install` refuses it there. The fix is tracked as GIS-620.

Until this is fixed, read the GENERO column of `fglpkg search` before installing
from an Artifactory repository.

## `publish --dry-run` makes one read

It uploads nothing and creates nothing. It does ask the registry whether this
version is already published, before anything else, and the banner now says so.
With no publish target configured, that question goes to the public registry
and carries the package's name.
